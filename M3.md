# M3 — ONNX Runtime and model registry

The M3 adapter uses `ort 2.0.0-rc.11` with `load-dynamic`, `std`, and no
download-binaries feature. Applications provide an installed ONNX Runtime
dylib through `ORT_DYLIB`; the inference path never downloads a model or
runtime. The dylib must be compatible with the ort API version (1.23).

`models/m3_identity.toml` points at the canonical locally generated,
checked-in `models/fixtures/m3_identity.onnx` opset-13
ONNX arithmetic graph. `tools/generate_fixture.py` emits the graph deterministically.
It applies the standard Relu clamp, accepts `[batch, channel, height, width]`
with symbolic dimensions, and returns the same non-negative f32 tensor as
`mask`. The model and license hashes
are pinned in the manifest; the graph has no third-party weights and is
redistributable under the repository license.

Validation order is intentionally fail-closed: TOML schema and typed enum
validation; safe manifest-relative model and license paths; license hash;
model SHA-256; raw ONNX opset; runtime initialization; session construction;
input/output names, tensor types, ranks and declared dimensions; optional
output index; only then `Session::run`. Errors include model id, name and
expected/actual values where applicable. Output selection is by declared name,
never implicit first-output selection.

`preprocess_rgb` implements encoded RGB to f32 with channel order, scale then
mean/std, and NCHW/NHWC layout. `TensorOutput::to_alpha_mask` accepts the four
single-channel layouts `[1,1,H,W]`, `[1,H,W,1]`, `[H,W]`, and `[1,H,W]`.
`apply_output_transform` supports sigmoid, clamp, safe constant-tensor min/max,
and finite checks.

`SessionPool` constructs exactly the requested number of sessions once, leases
one session per checkout, blocks when all workers are busy, and returns the
session on lease drop. Zero workers is rejected. `ProviderReport` records the
requested provider, attempted chain, active provider, and fallback reason. CPU
is the only positively claimed active provider in the default build. CoreML and
CUDA are explicit feature gates and are actually registered with CPU fallback
disabled for the requested-provider attempt. A successful feature session is
reported active under that provider; registration/session failure is captured,
then a separate CPU session is built only when fallback is allowed (with a
visible warning). Feature-disabled requests are reported as not attempted.

Commands:

```text
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --offline -- -D warnings
cargo test --workspace --offline
ORT_DYLIB=/path/to/libonnxruntime.dylib cargo run -p bgremove-cli -- inspect-model
ORT_DYLIB=/path/to/libonnxruntime.dylib cargo run -p bgremove-bench -- m3-smoke
```

The smoke command writes `runs/m3-ort/report.json` with stable manifest-relative
model identifiers (live inspection retains absolute diagnostic paths) and
manifest/model hashes,
graph metadata, provider report, worker bound, two deterministic tensor runs,
and output hashes. Runtime-dependent smoke/inspection requires an external
installed dylib and is deliberately not satisfied by a fake implementation.
