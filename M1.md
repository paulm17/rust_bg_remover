# M1 workspace and typed pipeline

The repository is now a Cargo workspace with seven crates under `crates/`:

* `bgremove-core` owns invariant-checked canonical RGB, alpha, trimap, matte,
  foreground, prompt, geometry, configuration, stage traits, and `Pipeline`.
* `bgremove-ort` is the deliberately deferred ONNX Runtime boundary.
* `bgremove-models` owns declarative TOML model-manifest metadata and inspection
  validation, including source, version, licence, intended-use, and opset
  metadata; checkpoint loading and hash enforcement begin in M3.
* `bgremove-matting` and `bgremove-color` provide the M1 identity/no-op stage
  implementations. Morphology, matting, colour recovery, and compositing are
  later milestones.
* `bgremove-cli` provides `bgremove run`, `mask`, and `inspect-model`.
* `bgremove-bench` preserves M0 `validate`, `baseline`, and `check`, and adds
  M1 `run` and `compare`.

Run commands from the repository root. Every M1 run or mask output directory
contains a canonical `resolved-config.json` with defaults resolved for the
input dimensions. The M1 artifacts are deterministic JSON skeletons and do not
claim to decode/resize/encode the source as a finished background remover.
The shared transitional loader applies EXIF orientation exactly once for both
CLI and benchmark runs, then preserves the canonical pixel grid without M2
resampling or output encoding.

```text
cargo run -p bgremove-cli -- run --input test_images/reference/1.png
cargo run -p bgremove-cli -- mask --input test_images/reference/1.png
cargo run -p bgremove-cli -- inspect-model --manifest models/noop.toml
cargo run -p bgremove-bench -- run --input test_images/reference/1.png
cargo run -p bgremove-bench -- compare --left runs/m1-skeleton/run.json --right runs/m1-skeleton/run.json
cargo run -p bgremove-bench -- check
```
