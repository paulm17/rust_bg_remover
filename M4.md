# M4 — IMG.LY IS-Net / DIS baseline

The M4 adapter is a typed, CPU-first IS-Net path built on the M3 verified
manifest/session pool. The IMG.LY profile uses the pinned JavaScript contract:
encoded RGB is resized to an exact 1024x1024 square with corner-aligned
bilinear interpolation and per-channel uint8 `Math.round`, then laid out NCHW
as `(u8 - 128) / 256`. Model output is direct and finite, with clamp only;
there is no implicit sigmoid or min/max normalization. The restored mask is
converted to uint8 and resized by the same bilinear routine to the canonical
source dimensions. Cutouts keep the canonical source RGB and store straight
alpha.

The separate `rembg-dis` profile uses u8 RGB resized with the documented
Lanczos3 implementation, divides every channel by the global maximum of the
resized image (with a safe epsilon), subtracts 0.5, uses NCHW, then applies
safe per-image min/max to direct output before u8 Lanczos3 restoration. It is
opt-in metadata and can never silently replace `imgly-isnet`.

The rembg compatibility fixture was generated in a temporary Python
environment with Pillow `10.4.0` by
`tests/fixtures/m4/generate_rembg_pillow_fixture.py`; its tracked JSON has
SHA-256 `c5abef407ae7c77ee9e218801e4d1a3985f16370276c7eeedc32e75e34a2d13c`.
For the fixed 3x2 edge/ramp image, image-crate Lanczos3 differs from Pillow
LANCZOS by measured input-resize max/mean `5`/`0.3172905525846702` u8 and
normalization max/mean `0.019607849214591244`/`0.0012442842930558472` f32;
the enforced normalized-f32 bounds are `0.019608`/`0.001245`, and the 3x2
mask restoration happened to match exactly. These are recorded compatibility
limits, not a claim of Pillow byte identity. The Rust test also checks global
resized-image maximum normalization and constant/non-finite min/max handling.

## Provenance and availability

The three manifests register one `isnet` algorithm family with `fp32`, `fp16`,
and `quantized` encodings. They pin source commit
`12f56cc4f2a90d624e165a715748d22efc7a1d93`, model bytes and licence hashes,
input/output names, shape, type, and opset 15. The supplied reference-tree
files are ignored by the root repository and are never downloaded by normal
inference. If a file is absent or its hash differs, verification fails closed.

`tests/fixtures/m4/reference.js` is the sole parity-artifact generator: it is
a dependency-free transcription sourced from the pinned JavaScript
implementation and runs the real model with the temporary
`onnxruntime-node@1.21.0` package. Its canonical output is tracked
`tests/fixtures/m4/parity.json`; the generator compares the Rust raw artifact
and computes the recorded max/mean errors. The accepted
`runs/m4-isnet/report.json` was then produced by the real CPU run with official
ORT 1.23.2 and embeds that generated evidence. Cross-runtime comparison of
the fixed 3x2 fixture measured raw f32 maximum absolute error
`5.960464477539064e-8` and mean absolute error `2.233946361229755e-11`;
declared limits are `1e-6` and `1e-7`. Input tensors and restored uint8 masks
matched exactly for 3x2 landscape, 2x3 portrait, and 5x3 odd-sized fixtures.
The tracked full input tensor is
`tests/fixtures/m4/reference-landscape.tensor.f32le` (12,582,912 bytes;
SHA-256 `406348a9ead28b8ee1e72d6def88231f7779d70e658dfadd1f975f381703327f`).
The tracked full raw reference is
`tests/fixtures/m4/reference-landscape.raw.f32le` (4,194,304 bytes; SHA-256
`1fe02354161ace92e06be71241c88d70ecca60ab8c14ed023031bfd3f688dfed`). The
three complete cutouts are tracked beside them. The official development
runtime was `onnxruntime-osx-arm64-1.23.2`.

The smoke artifact contains the tracked reference fixture records, stable
full tensor/raw/cutout evidence, explicit profile and encoding names, CPU
provider metadata, numeric tolerance/verdict data, and no timestamps or
machine-dependent paths. The implementation's Lanczos3 kernel is documented
as a deterministic compatibility path; it is not claimed to be byte-identical
to Pillow LANCZOS; the pinned fixture records the measured divergence.

The official ORT 1.23.2 inspection was also run for all three supplied
encodings. Each reported `input`/`output`, `f32`, `[1,3,1024,1024]` /
`[1,1,1024,1024]`, and opset 15 before inference.
